# Document Template Standard

> Athena 项目所有设计文档的强制结构规范。
> 版本：v1.0
> 生效日期：2026-08-05
> 适用范围：docs/ 下所有设计文档、ADR、RFC

---

## 强制结构

所有 Athena 设计文档必须按以下顺序包含九个章节。缺失任一章节的文档不被接受。

```
1. Background（背景）
2. Problem（问题）
3. Goals（目标）
4. Non-goals（非目标）
5. Design（设计）
6. Alternatives（替代方案）
7. Risks（风险）
8. Future Work（未来演进）
9. References（参考）
```

---

## 章节规范

### 1. Background（背景）

**目的**: 让读者在 30 秒内理解"为什么会有这篇文档"。

**必须包含**:
- 项目当前所处的阶段（Phase 0/1/2...）
- 触发这篇文档的事件或决策需求（"因为我们决定引入 X..."）
- 相关历史背景（如果有之前的讨论或决策）

**反例**（不充分的背景）:
> 我们需要一个缓存系统。

**正例**（充分的背景）:
> Athena Phase 2 将上线搜索服务。架构审查（ADR-002）指出搜索 P50 延迟需 < 100ms，
> 但 PostgreSQL 的全文搜索在 100K 文档量下 P50 已达到 350ms。
> 我们需要一个独立的缓存层来满足性能目标。本文档设计该缓存层的架构。

---

### 2. Problem（问题）

**目的**: 精确定义文档要解决的具体问题。

**必须包含**:
- 问题的技术表述（可量化）
- 当前状态（如果没有解决方案会怎样）
- 受影响的范围（哪些模块、哪些用户）

**反例**（模糊的问题）:
> 搜索太慢了。

**正例**（精确的问题）:
> 当前搜索 P50 延迟为 350ms，P99 为 1200ms。Phase 2 目标是 P50 < 100ms，P99 < 500ms。
> 分析显示 80% 的搜索请求命中了 top 100 热门查询，这些查询占据了 60% 的搜索流量。
> 影响范围：Search Context、Content API、未来 Web 前端。

---

### 3. Goals（目标）

**目的**: 定义成功的标准。完成后如何判断"问题已解决"。

**必须包含**:
- 量化的成功指标（数字 + 单位 + 时间范围）
- 定性的成功描述（用户体验、开发者体验）
- 优先级（如果目标之间有冲突，哪个优先）

**格式**:
```
- [ ] 目标 1: 量化的成功指标
- [ ] 目标 2: 量化的成功指标
- [ ] 目标 3: 定性描述
```

**优先级标注**: 在目标后标注 `(P0)`, `(P1)`, `(P2)` 表示优先级。

---

### 4. Non-goals（非目标）

**目的**: 明确本文档**不**覆盖的范围，防止范围蔓延。

**必须包含**:
- 明确排除的功能或场景
- 说明为什么排除（留给其他文档、留给未来阶段、根本不做）

**格式**:
```
- 不做 X — 原因：留给 Phase 3 的 Y 文档处理
- 不覆盖 Z — 原因：超出本文档的技术范围
```

**重要**: Non-goals 不是"我们不想做"。而是"这件事可能有人会问，所以提前说清楚不在本文档范围内"。

---

### 5. Design（设计）

**目的**: 核心章节。详细描述解决方案。

**必须包含**:
- 架构图或数据流图（推荐 Mermaid）
- 关键组件的接口定义（代码块或伪代码）
- 数据模型变更（如有）
- API 变更（如有）
- 迁移计划（如果影响已有系统）

**子章节**（按需选用）:
- 5.1 Overview（总览）
- 5.2 Component Design（组件设计）
- 5.3 Data Flow（数据流）
- 5.4 API / Interface（接口定义）
- 5.5 Migration Plan（迁移计划）
- 5.6 Security Considerations（安全考量）

---

### 6. Alternatives（替代方案）

**目的**: 证明当前方案是经过深思熟虑的选择，而非唯一想到的方案。

**必须包含**:
- 至少 2 个替代方案
- 每个替代方案的：
  - 简要描述
  - 优点（至少 2 条）
  - 缺点（至少 2 条）
  - **为什么不选**（这是最重要的——必须给出明确的技术理由）

**格式**:

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|-----------|
| A | ... | ... | 因为... |
| B | ... | ... | 因为... |
| **C (采用)** | ... | ... | — |

---

### 7. Risks（风险）

**目的**: 诚实面对方案的风险和不确定性。

**必须包含**:
- 技术风险（可能的技术难点）
- 运维风险（对已有系统的影响）
- 人员风险（需要的技能是否在团队中）
- 每个风险的**缓解措施**（不能只是列出风险）

**格式**:

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| ... | 高/中/低 | 高/中/低 | ... |

**风险概率定义**:
- 高：几乎肯定会遇到
- 中：有一定可能遇到
- 低：不太可能但需要知晓

---

### 8. Future Work（未来演进）

**目的**: 明确本文档不是终点——下一步做什么、什么情况下需要重新审视。

**必须包含**:
- 短期（1-3 个月）的后续工作
- 长期（6-12 个月）的演进方向
- **触发条件**: 什么情况下需要重新打开这篇文档？

**格式**:
```
短期（Phase X）:
- ...

长期（Phase Y+）:
- ...

重新审视触发条件:
- 当 X 达到 Y 阈值时
- 当 Z 技术成熟时
```

---

### 9. References（参考）

**目的**: 提供上下文链接，帮助读者深入理解。

**必须包含**:
- 相关 ADR / RFC 编号和链接
- 相关设计文档链接
- 外部参考资料（论文、博客、文档）
- 讨论记录（Issue、Discussion 链接）

**格式**:
```
- [ADR-001](adr/ADR-001-project-init.md) — 项目初始化决策
- [RFC-001](rfc/RFC-001-backend-language.md) — 后端语言选型
- 外部: [Title](https://...) — 简要说明
```

---

## 检查清单

提交文档前，确认以下所有项：

- [ ] 九个章节全部存在
- [ ] Background 解释了"为什么会有这篇文档"
- [ ] Problem 是具体的、可量化的
- [ ] Goals 有明确的成功标准
- [ ] Non-goals 排除了可能被误解的范围
- [ ] Design 包含架构图或接口定义
- [ ] Alternatives 至少包含 2 个替代方案，每个有不选理由
- [ ] Risks 包含缓解措施
- [ ] Future Work 包含重新审视的触发条件
- [ ] References 包含所有引用的文档链接
- [ ] 文档没有"TODO"或"待定"的占位符（除非明确标注为 Draft）

- `docs/adr/` — 所有 ADR 必须遵守
- `docs/rfc/` — 所有 RFC 必须遵守
- `docs/architecture/` — 所有架构设计文档必须遵守

## Documentation as Code 标准

Blueprint 的目标不是给人阅读，而是让未来任何 AI 在不依赖聊天上下文的情况下独立理解项目并持续开发。

### 三条质量标准

1. **可视化** — 设计必须有图（Mermaid / C4 / 时序图 / 状态机）。画不出图 = 设计不清晰。
2. **成熟度** — 设计必须形成 ADR 或 RFC。构不成 ADR/RFC = 设计不成熟。
3. **完整性** — AI 必须能依据文档独立实现。AI 实现不了 = 文档不完整。

### 验收测试

1. 新 AI 实例读取文档 → 能否独立画出设计图？
2. 新 AI 实例读取文档 → 能否独立写出对应代码？
