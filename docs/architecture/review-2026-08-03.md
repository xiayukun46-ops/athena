## 1. 架构健康度评估

### 1.1 总体评价：良好

| 维度 | 评分 | 说明 |
|------|------|------|
| 设计一致性 | A | Knowledge Model → DDD → ER/Graph → Event 四层设计一致，上下位关系清晰 |
| 文档完整性 | A | 治理/架构/领域/API/数据库/指南六大领域全覆盖 |
| 架构原则遵循 | A | 八个 First 原则在宪法和所有文档中得到贯彻 |
| 可演进性 | A- | Modular Monolith 为微服务拆分预留了明确的接口边界和触发条件 |
| 安全性设计 | B+ | 安全架构文档完整，但 Phase 0 无法验证实际实现 |

### 1.2 设计优势

**1. Knowledge Triangle 三层模型**
Entity - Relation - Statement 的三层分离设计是 Athena 最核心的创新。Statement 作为可溯源的最小知识单元，使每个事实都能追溯到原始文章，支持冲突保留（多数派/少数派观点并存）而非粗暴二选一。这个设计在业界知识图谱产品中少见。

**2. 插件原生的架构决策**
将"所有业务功能都是插件"作为架构原语而非后期重构目标。五类插件接口（Source / Processor / Storage / AI / UI）+ 统一的依赖注入和生命周期管理，为十年的扩展性打下了基础。

**3. PostgreSQL + Neo4j 双存储的明确定位**
PG 管"存"（事务一致性、聚合查询），Neo4j 管"查"（路径遍历、子图匹配）。通过领域事件异步同步，事件重放可重建 Neo4j 图。这种"一个 Source of Truth + 多个读优化视图"的模式是 CQRS 的正确前身。

**4. DDD 战术设计的完整性**
六个限界上下文的聚合根、实体、值对象、仓储接口、领域服务都给出了伪代码级定义。上下文间通过事件解耦（非直接 API 调用），为未来拆分到微服务铺平了道路。

## 2. 风险识别

### 2.1 高风险

| ID | 风险 | 影响 | 缓解建议 |
|----|------|------|----------|
| R1 | EAV 属性模型（knowledge_entity_properties）在实体数量百万级时查询性能下降 | High | Phase 2 对高频属性建立物化视图或 JSONB 冗余列 |
| R2 | PG ↔ Neo4j 事件同步的一致性问题——PG 写入成功但 Neo4j 同步失败 | High | 引入 Outbox Pattern，事件先写入 `system_event_log`，再由独立 Worker 投递至 Neo4j |
| R3 | AI 提取的知识质量不可控——低质量声明污染知识图谱 | High | Statement 审核流程必须在上线前就位；引入知识质量评分仪表盘 |

### 2.2 中风险

| ID | 风险 | 影响 | 缓解建议 |
|----|------|------|----------|
| R4 | Statement 声明冲突解决策略未定义优先级规则 | Medium | 在 KnowledgeAggregationService 中明确定义冲突仲裁规则（置信度 → 来源数 → 时效性 → 人工） |
| R5 | 实体合并（EntityMerged）后，已缓存的关系查询可能返回过期数据 | Medium | 引入 Cache Invalidation 策略；合并事件触发相关缓存清除 |
| R6 | GraphQL Schema 的 N+1 问题——entity → relations → target entity 的深度嵌套 | Medium | 使用 DataLoader 批处理；限制查询深度 |

### 2.3 低风险

| ID | 风险 | 影响 | 缓解建议 |
|----|------|------|----------|
| R7 | API 版本管理策略在 Phase 0 仅定义了规则，未实现自动化 | Low | Phase 2 使用 OpenAPI 3.1 + 工具自动生成 API 文档和版本检查 |
| R8 | 多语言知识对齐的正确率依赖 AI 模型性能 | Low | 建立多语言实体对齐评测集，定期回归 |

## 4. 一致性检查

### 4.1 术语一致性

检查范围：Knowledge Model ↔ DDD Detailed ↔ ER Diagram ↔ Graph Model ↔ API Design

| 术语 | KM | DDD | ER | Graph | API | 一致？ |
|------|:--:|:---:|:--:|:-----:|:---:|:------:|
| Entity（知识实体） | ✓ | KnowledgeEntity | knowledge_entities | (:Entity) | /v1/entities | ✓ |
| Relation | ✓ | KnowledgeRelation | knowledge_relations | [:RELATION] | /v1/relations | ✓ |
| Statement | ✓ | Statement | knowledge_statements | (:Statement) | /v1/statements | ✓ |
| Source | - | Source | content_sources | (:Source) | /v1/sources | ✓ |
| Article | - | Article | content_articles | (:Article) | /v1/articles | ✓ |
| Confidence | 0.0-1.0 | Confidence(0.0-1.0) | NUMERIC(3,2) | Float(0.0-1.0) | float | ✓ |
| EntityType | 8 types | EntityType enum | VARCHAR(50) CHECK | entity_type property | query param | ✓ |

**结论**: 核心术语在五个层面完全一致，无冲突。

### 4.2 ID 命名约定

| 上下文 | 前缀 | 示例 |
|--------|------|------|
| Source | src_ | src_abc123 |
| Article | art_ | art_def456 |
| Entity | ent_ | ent_ghi789 |
| Relation | rel_ | rel_jkl012 |
| Statement | stmt_ | stmt_mno345 |
| User | usr_ | usr_pqr678 |

**结论**: ID 前缀约定在 API Design 中定义，但在其他文档中未明确。建议在 Shared Kernel 文档中统一记录。
