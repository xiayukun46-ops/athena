# 01 — Product Strategy

> 如何从愿景走到产品。阶段性目标。取舍原则。

---

## 定位

Athena 是 **AI 驱动的全球知识平台**。

不是：
- ❌ 新闻聚合器（那是内容管道的一部分，不是产品）
- ❌ AI 聊天机器人（那是交互方式，不是产品）
- ❌ 搜索引擎（那是功能，不是产品）

是：**把全球信息转化为可信、结构化、可查询的知识图谱。**

---

## 目标用户

| 阶段 | 用户 | 场景 |
|------|------|------|
| Phase 2-3 | 内部 / Alpha 测试者 | 验证知识提取和查询能力 |
| Phase 4 | 知识工作者、研究者、记者 | 深度研究、事实核查、趋势追踪 |
| Phase 5 | 开发者、企业 | 基于 Athena API 构建应用 |

## 为什么这个顺序

先服务"信息密集型"用户（研究者、记者）而非普通消费者。原因：

1. **容忍度高**：研究者愿意验证信息准确性，容忍 AI 的瑕疵
2. **价值密度高**：深度研究的价值远大于碎片化阅读
3. **反馈质量高**：专业用户的反馈帮助迭代知识模型

替代方案：先做大众化新闻 App。**不选理由**：大众用户对 AI 错误的容忍度低，且竞争激烈（今日头条、Google News）。

---

## 核心价值主张

```
从"读文章"到"问知识"

传统方式: 搜索 → 读 10 篇文章 → 自己总结
Athena 方式: 提问 → 结构化答案 + 溯源 + 不同观点
```

三条产品线：
1. **Knowledge Graph（知识图谱）**：实体、关系、声明、时序
2. **Q&A Engine（问答引擎）**：基于 RAG 的可信问答
3. **Discovery（发现引擎）**：趋势检测、关联发现、个性化推送

## 取舍原则

当设计发生冲突时，按以下优先级决策：

1. **准确性 > 速度**：宁可慢，不可错
2. **溯源性 > 流畅性**：知识必须有出处，即使表达不够优美
3. **开放性 > 控制**：平台 API 优先于自有 UI
4. **长期 > 短期**：10 年架构优于 3 个月快跑

---

## 不做的事

- 不做社交功能（评论、点赞、分享）
- 不做内容创作（Athena 理解内容，不生产内容）
- 不做个性化推荐信息流（Phase 4 可能考虑，但不是核心）
- 不做付费内容 / 付费墙
