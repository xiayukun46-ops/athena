## 1. 序言

### 1.1 宪法的地位

本文档是 Athena Knowledge Platform 的**最高法律文件**。它定义了项目的根本规则——什么可以做、什么不能做、如何做决策、如何演进。所有其他项目文档（ADR、RFC、Coding Standard、API Guide）均从属于本宪法，且不得与本宪法冲突。

本宪法不是指导性建议，而是**强制约束**。违反宪法的代码必须被拒绝合并。违反宪法的架构决策必须被撤销。宪法面前，没有例外。

### 1.2 为什么项目需要宪法

大多数软件项目没有宪法。它们依靠惯例、代码审查、Tech Lead 的个人判断来维持质量。这在 3 个月的项目中可行。在 10 年的项目中不可行——10 年间，团队会换 5 批人，Tech Lead 会换 3 个，最初的惯例会被遗忘。

宪法解决的根本问题是：**10 年后，一个从未见过原始团队的新成员，能通过阅读本宪法理解这个项目"法律"的边界在哪里。**

宪法做了三件事：
1. **划定底线**——什么永远不可以做
2. **建立程序**——遇到决策分歧时怎么解决
3. **保障演进**——宪法本身如何修改（使它不会成为僵化的枷锁）

### 1.3 宪法的使用方式

- **新成员入职**：第一份阅读材料。理解"这里怎么做事"。
- **PR Review**：审查标准。代码是否符合宪法的质量要求？
- **架构讨论**：最终裁决依据。当两个人争执不下时，回到宪法——谁的主张更符合宪法原则？
- **季度审查**：检查项目是否在偏离宪法。如果有偏离，要么纠正行为，要么修改宪法。

## 2. 八项核心原则

八项原则按优先级从高到低排列（P1 最高）。前四项（P1-P4）是**硬约束**——违反的代码直接拒绝。后四项（P5-P8）是**强约束**——违反需要书面说明理由并获得批准。

---

### P1. Documentation First（文档优先）

**规则**: 无设计文档，不接受代码。

**详细解释**:

代码是"How"——怎么实现的。文档是"Why"——为什么这样实现。代码会过时、会被重写、会被替换。但设计意图——为什么选择这个架构、为什么拒绝那个方案——是项目唯一不会贬值的资产。

文档优先不是"多写注释"。而是：
- 任何新功能：先写设计文档（RFC 或 ADR），Approved 之后才能写代码
- 任何架构变更：先更新 ADR，记录变更原因和影响
- 任何 API 变更：先更新 OpenAPI 规范，再写实现
- 每次 PR：如果涉及设计变更，必须附带文档更新

**为什么是 P1（最高优先级）**:

没有文档的代码是债务。5 年后，能解释"这段代码为什么这样写"的人已经离职了。文档是项目对抗时间的唯一武器。

**替代方案: Code-as-Documentation**

主张"代码就是文档——命名清晰、结构清楚就够了"。
- 优点：不增加额外工作量，代码不会过时（文档可能过时）
- 缺点：代码解释不了"为什么"。你可以从代码看出"这里用了一个 LRU Cache"，但看不出"我们试过 Redis Cache 但发现 80% 命中率集中在 20% 的 key，所以改用 LRU"。
- **不选理由**：10 年尺度上，代码中的"为什么"会被抹去（重构、重写、人员变动）。

**执行方式**:
- CI 自动检查关键文档是否存在（`PROJECT_CONSTITUTION.md`, `docs/README.md` 等）
- PR 模板包含"文档是否已更新"的 checkbox
- 无文档的功能 PR → Reviewer 不应 Approve

**对现有设计的确认**: 本宪法本身就是 Documentation First 的产物——它先于所有代码存在。

---

### P2. Architecture First（架构优先）

**规则**: 先定义接口和契约，后写实现。

**详细解释**:

架构优先不是"先画完所有的 UML 图再写第一行代码"——那是瀑布模型，已死。架构优先的意思是：在任何模块的实现之前，先定义它对外暴露的**接口**。

接口是模块间的"法律合同"。它定义了：输入什么、输出什么、什么异常情况会抛什么错误。实现可以重写——只要接口不变，消费者就不受影响。

对于 Athena 这意味着：
- 每个限界上下文（Content, Knowledge, Search, AI）对外暴露一组 Python ABC（抽象基类）
- 模块间不直接导入对方的实现类——只导入接口
- 跨上下文通信只通过 Domain Events（事件也是接口的一种）

**为什么是 P2**:

接口是项目中变化最慢的部分。一个好的接口可以用 5 年，而它的实现可能被重写 10 次。先定义接口意味着先把"最难改的东西"定下来。

**替代方案: 敏捷迭代（先写代码，后抽象接口）**

- 优点：快速、灵活、在探索阶段减少前期设计浪费
- 缺点：当代码量超过 50K 行后，缺乏接口的模块间耦合变得无法管理
- **不选理由**：Athena 从第一天就不是"探索阶段"——我们用 Phase 0 完成了所有设计。我们不是在探索"做什么"，我们是在执行"怎么做"。

**执行方式**:
- 新模块必须先通过接口设计评审（ADR）
- 接口变更需要标注 Breaking Change 并提供迁移期
- PR Review 中，Reviewer 应检查是否遵守了接口边界

---

### P3. Domain First（领域优先）

**规则**: 代码组织围绕领域模型（Bounded Context），而非技术分层（Controller / Service / Repository）。

**详细解释**:

传统 Web 项目按技术分层组织：
```
src/controllers/    ← 所有控制器
src/services/       ← 所有服务
src/models/         ← 所有模型
src/utils/          ← 所有工具函数
```

Athena 按领域组织：
```
src/content/        ← Content Context 的全部代码
  domain/           ← 领域模型（Entity, Value Object, Domain Service）
  application/      ← 应用服务（用例编排）
  infrastructure/   ← 基础设施（数据库实现、外部 API）
  interfaces/       ← 接口层（REST API、事件处理器）

src/knowledge/      ← Knowledge Context 的全部代码
  domain/
  application/
  infrastructure/
  interfaces/
```

**为什么这样组织**:

技术分层（Controller/Service/Repository）的好处是统一——你知道每个文件在哪个目录。但当系统有 6 个领域时，改一个业务需求（比如"实体合并后通知搜索更新"）需要跨 3 层、改 6 个文件、在不同目录间跳转。

领域内聚的好处是：和 Content 相关的所有代码都在 `src/content/` 下。未来 Content 要拆成独立微服务？把整个目录拎出去就行。

**为什么是 P3**:

领域模型反映的是"Athena 是做什么的"——这是 10 年不变的。技术分层反映的是"代码怎么写"——这 2-3 年可能就变了。

**替代方案: 传统 MVC 分层**

- 优点：新人容易上手（学过 MVC 的都会）
- 缺点：跨层修改频繁（改一个需求 → controller + service + model 都改），领域概念分散
- **不选理由**：MVC 适合 CRUD 应用。Athena 的核心复杂度不在 CRUD，而在领域逻辑（实体消歧、关系推理、声明聚合）。

**执行方式**:
- `src/` 目录结构以 Bounded Context 为一级目录
- 不可在 `src/content/` 中直接导入 `src/knowledge/domain/` 的实现类（只导入接口）
- 新增 Bounded Context 需要 ADR 审批

---

### P4. API First（API 优先）

**规则**: 所有用户可见功能，先定义 API 契约（OpenAPI 3.1），再写实现。

**详细解释**:

API 是 Athena 对外的"宪法"。Web 前端、Mobile App、第三方集成——所有消费者都通过 API 与 Athena 交互。如果我们先写后端实现再定义 API，结果往往是 API 暴露了实现细节、不够正交、不适合多种客户端。

API First 的流程：
1. 设计 API 端点：URL、Method、Request Schema、Response Schema
2. 写入 OpenAPI 3.1 规范文件（`docs/api/openapi.yaml`）
3. PR Review——前端和平台团队审查 API 是否适合他们的消费场景
4. Approved 后，后端和前端并行开发

**为什么是 P4**:

API 是变化成本最高的部分。后端实现改了不影响消费者——API 改了就影响所有人。先定 API 意味着先把"最难改的东西"定下来。

**替代方案: 后端驱动（先写实现，自动生成 API 文档）**

- 优点：对后端开发更快（不需要预先设计）
- 缺点：API 设计受实现细节影响（如数据库表结构泄露到 API 响应中），不适合多客户端
- **不选理由**：Athena 的 Phase 5 定位是开放平台——API 是产品本身，不是"后端的附属品"。

**执行方式**:
- 所有 API 端点在 OpenAPI 3.1 中有定义
- API 版本化：`/v1/`, `/v2/`
- Breaking Change 保留旧版本 ≥ 6 个月
- 前端和后端基于同一份 OpenAPI 规范并行开发

---

### P5. Plugin First（插件优先）

**规则**: 核心保持最小化。所有业务能力——内容源、AI 模型、数据存储、处理器——通过插件接入。

**详细解释**:

Athena 的核心框架只提供：路由、生命周期管理、依赖注入、事件总线。除此之外的所有功能——RSS 抓取、HTML 清洗、NER 提取、翻译、PostgreSQL 存储、Neo4j 图同步——都是插件。

这听起来像过度设计。但请考虑：5 年后，可能有人写了一个全新的内容源类型（比如脑机接口直接传输文本）。如果他们需要改核心代码才能接入——他们可能选择不接入。Plugin First 意味着核心永远不需要为扩展而改动。

**为什么是 P5**:

插件系统是对抗"核心膨胀"的唯一结构性手段。每个成功的平台（VSCode、Chrome、WordPress）都经历过从"核心功能丰富"到"核心尽量小"的痛苦重构。Athena 从第一天就插件化，避免这个痛苦。

**替代方案: 核心集成所有功能（Monolithic Core）**

- 优点：初期开发速度快（不需要设计插件接口）
- 缺点：2 年后核心代码量爆炸，改一个功能怕影响其他功能，项目僵化
- **不选理由**：适合不需要扩展的项目。Athena 的核心需求就是"可扩展"。

**执行方式**:
- 五类插件接口：`ISourcePlugin`, `IProcessorPlugin`, `IStoragePlugin`, `IAIProviderPlugin`, `IUIPlugin`
- 新功能先评估：是否可以以 Plugin 形式实现？如果是，写 Plugin
- 仅当功能是"框架级别"的（如新的生命周期阶段）才修改核心

### P6. AI First（AI 优先）

**规则**: AI 不是功能，是架构原语。整个数据管道从设计之初就支持 Embedding、RAG、Agent 工作流。

**详细解释**:

大多数项目把 AI 当作"附加功能"——先建好平台，再"加一个 AI 问答功能"。结果是：数据库不支持向量、API 不支持异步任务、数据管道不支持 LLM 输入/输出。

Athena 反其道而行：AI 是数据管道的默认处理方式。
- 内容采集后 → 默认经过 AI 摘要
- 文章入库后 → 默认经过 AI NER 提取
- 实体创建后 → 默认生成 Embedding 向量
- 用户搜索 → 默认使用 Hybrid Search（全文 + 向量）

**为什么是 P6**:

2026 年开始建设知识平台，如果不以 AI 为架构原语，等于用内燃机设计来造电动车——三年后会发现所有架构假设都是错的。

**替代方案: 先建平台，后加 AI**

- 优点：降低前期复杂度，降低 AI 依赖风险
- 缺点：数据库 Schema 不预留向量列、API 不支持异步、事件管道不支持 AI 任务——后期加 AI 等于重构
- **不选理由**：2026 年的 AI 成熟度（GPT-5, Claude-4）已经到了"基础设施"级别，不是"实验性功能"。

**执行方式**:
- PostgreSQL 使用 pgvector 扩展（向量存储）
- 所有 AI 调用设计为异步（202 Accepted Pattern）
- Domain Events 触发 AI Pipeline（ArticleFetched → Entity Extraction → Knowledge Graph Update）
- 每个 LLM 调用的输入/输出写入审计日志
- Prompt 模板纳入版本管理

### P7. Test First（测试优先）

**规则**: TDD——先写测试，后写实现。测试是设计工具，不是验证工具。

**详细解释**:

很多人误解 TDD 为"先写测试保证不写 Bug"。TDD 的真正价值不是 Bug 预防——是**设计反馈**。

当你先写测试时，你会被迫思考："这个函数的输入是什么？输出是什么？什么情况下抛异常？"这些问题就是接口设计。如果写测试很痛苦（需要 Mock 太多东西、Setup 太长），说明你的设计有问题——耦合太高。

**为什么是 P7**:

10 年项目中，测试是唯一保证"改了 A 没坏 B"的安全网。没有测试的代码是不可重构的——而 10 年的项目必然经历多次大重构。

**替代方案: 先写代码，后补测试**

- 优点：初期开发速度更快
- 缺点：补的测试测的是"实现"，不是"设计"。如果实现本身有设计问题，测试只会固化这些问题
- **不选理由**：补的测试覆盖率通常不完整（"核心路径测了，边缘条件没测"）

**执行方式**:
- CI 中覆盖率门禁不可绕过
- 覆盖率目标：核心域 ≥ 90%、应用层 ≥ 80%、基础设施 ≥ 70%
- 代码覆盖率相比 main 分支不得下降
- AI 输出使用专门评测框架（非传统 unit test）

### P8. Security First（安全优先）

**规则**: 零信任——默认不信任任何输入，包括 AI 的输出。安全不是一个阶段（"上线前审查一次"），而是一个贯穿设计、开发、测试、运维的持续过程。

**详细解释**:

Athena 的安全挑战比传统 Web 应用更大——因为它是一个 AI 系统。
- 用户输入可能包含 Prompt Injection（通过精心构造的文本操纵 Agent 行为）
- AI 输出可能包含模型泄露的训练数据
- 外部内容源可能投毒（发布虚假信息操纵知识图谱）
- Agent 拥有工具调用能力，攻击面远超传统 API

**为什么是 P8**:

AI 系统被攻击的后果不仅是"数据泄露"——可能是"知识图谱被污染后向所有用户传播虚假信息"。这是系统级的信誉风险。

**替代方案: 上线前一次安全审查**

- 优点：简单、成本低
- 缺点：事后补救的成本远高于事前预防。一个被污染的实体可能需要数周才能清理
- **不选理由**：不安全——AI 系统的攻击面与传统 Web 应用不同

**执行方式**:
- 每次 PR 必须通过安全扫描（Trivy 依赖漏洞 + Gitleaks 密钥扫描）
- 所有输入在 API Gateway 边界验证
- SQL 和 Cypher 查询全部参数化（禁止字符串拼接）
- Agent 权限最小化（工具白名单 + 操作审批）
- AI 输入/输出 PII 脱敏
- 审计日志全量记录

## 3. 原则冲突时的优先级

八项原则在大多数情况下互补。但在某些场景下，它们会产生张力。以下定义冲突时的优先级规则：

### 3.1 冲突 1: Documentation First vs. 快速迭代

**场景**: "这个 Bug 修复很小，可以跳过文档更新吗？"

**裁决**: 不可以。Documentation First 是 P1 最高优先级。任何修改——无论大小——如果涉及设计意图的变化，都需要更新文档。一行代码的 Bug 修复（修正 typo）可以跳过文档。但改变了函数签名的 Bug 修复不行。

### 3.2 冲突 2: API First vs. 后端先行

**场景**: "前端还在设计，我们先写后端实现，API 后面再定义吧。"

**裁决**: 不可以。API 先于任何实现。但可以接受"先定义 API 骨架（OpenAPI Schema），后端和前端在此基础上并行开发"。

### 3.3 冲突 3: Plugin First vs. 开发速度

**场景**: "这个功能以 Plugin 实现需要设计接口 + 写 Plugin + 测试 Plugin，直接在核心里写只需要半天。"

**裁决**: 如果功能确定属于五类插件之一的范畴（新的内容源、AI 模型、存储引擎、处理器），必须做 Plugin。核心代码不接受"临时方案"。如果是全新的框架能力（如新增生命周期 Hook），可以在核心中实现并通过 ADR 审批。

### 3.4 冲突 4: Security First vs. 用户体验

**场景**: "Agent 的每次工具调用都需要人工审批，用户觉得太慢。"

**裁决**: 安全优先级高于体验。但团队应优化审批流程（如预授权常见操作、批量审批）而非取消安全控制。

### 3.5 冲突 5: Test First vs. 探索性代码

**场景**: "我在 Prototype 一个功能，还不确定怎么做，可以先写代码再写测试吗？"

**裁决**: 可以。标记为 `prototype/` 分支的实验性代码可以豁免 P7，但不能合并到 main。合并到 main 的任何代码都必须有测试。

## 4. 决策体系

Athena 的决策按层级递进。层级越高的决策，修改成本越高、参与人数越多。

### 4.1 决策层级表

| 层级 | 机制 | 适用范围 | 决策者 | 修改门槛 |
|------|------|----------|--------|----------|
| **L0** | 本宪法 | 根本原则、项目身份、治理框架 | 核心团队 ≥ 2/3 | RFC + 2/3 票 |
| **L1** | ADR | 重大架构决策（语言、框架、数据模型） | 核心团队 ≥ 2 人 Approve | 新 ADR |
| **L2** | RFC | 功能设计、API 变更、技术引入 | 核心团队决策 | 讨论 ≥ 7 天 |
| **L3** | PR Review | 日常代码实现、Bug 修复 | ≥ 1 人 Approve | 标准 PR 流程 |

### 4.2 L0 — 本宪法

- **范围**: 八项核心原则、决策体系、质量门禁、演进规则
- **修改**: 需 RFC + 核心团队 2/3 多数
- **不可绕过**: 即使核心团队全票同意，也不可临时绕过宪法（宪法不提供"快车道"）

### 4.3 L1 — ADR（Architecture Decision Record）

- **范围**: 影响系统全局或跨模块的架构决策
- **触发条件**: 选择编程语言、引入新存储引擎、变更 Domain Model、拆分/合并 Bounded Context、引入新的架构模式
- **流程**: 撰写 ADR → 核心团队至少 2 人 Approve → 归档
- **编号**: 连续编号（ADR-001, ADR-002...），不可删除或重用
- **状态**: `Proposed → Accepted / Rejected / Superseded / Deprecated`

**ADR 示例场景**:
- "我们应该用 Neo4j 还是 PostgreSQL AGE 做图数据库？" → ADR-003
- "Knowledge Entity 的 merger 逻辑应该放在 Domain Service 还是 Aggregate Root？" → ADR（如果涉及架构模式）

### 4.4 L2 — RFC（Request for Comments）

- **范围**: 功能设计、API 端点变更、技术选型
- **触发条件**: 新增 API 端点、修改现有 API Schema、引入新的第三方依赖、功能超过 200 行代码
- **流程**: 撰写 RFC → 社区讨论 ≥ 7 天 → 核心团队决策
- **结果**: Accept / Reject / Needs Revision

**RFC 示例场景**:
- "添加 /v1/entities/{id}/timeline 端点" → RFC（API 扩展）
- "将 NER Pipeline 从 spaCy 换成 transformers" → RFC（技术选型变更）

### 4.5 L3 — PR Review

- **范围**: 日常代码变更
- **要求**: ≥ 1 人 Approve + 所有 Quality Gates 通过
- **例外**: 紧急热修复可通过"Fast Track"流程（事后补 ADR）

## 5. 质量门禁

以下门禁均为**阻塞性门禁**（不通过 = 不能合并）。不可被 Approver 手动覆盖。

### 5.1 门禁清单

| # | 门禁 | 工具 | 自动/手动 |
|---|------|------|----------|
| 1 | Lint 通过 | ruff (Python), eslint (TS) | 自动 |
| 2 | 类型检查通过 | mypy --strict, tsc --noEmit | 自动 |
| 3 | 测试通过 | pytest, vitest | 自动 |
| 4 | 覆盖率不下降 | pytest-cov, codecov | 自动 |
| 5 | 安全扫描通过（无 HIGH/CRITICAL） | Trivy | 自动 |
| 6 | 密钥扫描通过 | Gitleaks | 自动 |
| 7 | 构建通过 | Docker build, package build | 自动 |
| 8 | 文档已更新 | Manual Check | 手动 |
| 9 | ≥ 1 人 Approve | GitHub PR Review | 手动 |
| 10 | Commit 符合 Conventional Commits | commitlint | 自动 |

### 5.2 门禁的不可绕过性

门禁 1-7 和 10 由 CI 自动执行，无法人为绕过。门禁 8-9 由 Reviewer 检查。

如果出现"CI 误报"（如 false positive 安全扫描），可以临时 suppress（通过注释标记 + Issue 追踪），但不能跳过门禁。

## 6. 演进规则

宪法不能成为僵化的枷锁。但修改宪法必须比修改代码更谨慎。

### 6.1 宪法修订流程

1. 提出者撰写 RFC，标题格式：`RFC-XXX: Constitution Amendment — {简述}`
2. RFC 中必须包含：
   - 修改哪一条原则
   - 为什么需要修改（"当时为什么这样定" + "现在为什么需要变"）
   - 修改后的完整文本
   - 对已有设计和代码的影响评估
3. 社区讨论 ≥ 14 天（普通 RFC 7 天，宪法修订 14 天）
4. 核心团队投票，≥ 2/3 多数通过
5. 旧版本完整保留，放入 `docs/governance/constitution-archive/`

### 6.2 技术演进

- 每季度进行一次**架构健康度评估**（Architecture Review）
- 评估内容：原则是否仍然适用？有没有需要更新的地方？有没有技术债务在累积？
- 技术债务需在 ADR 中**登记并设定偿还期限**。到期未偿还的债务升级为 Blocking Issue。
- 废弃技术（如 Redis Streams → Kafka 迁移）必须有**迁移计划**，不得突然移除。

### 6.3 向后兼容

- API 大版本更新（v1 → v2）：旧版本保留 ≥ 6 个月
- 数据迁移：支持**双写过渡期**（新旧 Schema 同时写入，读从旧 Schema 切到新 Schema）
- 插件接口变更：提供**适配层**，使旧插件在不修改代码的情况下能在新接口下运行至少一个主版本

## 8. 合规与执行

### 8.1 架构合规审查

- **频率**: 每季度一次
- **执行者**: Maintainers 指定 1-2 名审查员（可以是外部人士）
- **审查内容**: 代码组织是否符合 Domain First？模块间通信是否遵守 Event-only？是否有未经 ADR 的架构决策？
- **输出**: Architecture Compliance Report，公开在 `docs/adr/`

### 8.2 原则合规检查表

每个 Sprint 结束后，团队自检：

- [ ] 本 Sprint 是否引入了未经文档化的设计变更？
- [ ] 本 Sprint 是否引入了跨 Bounded Context 的直接调用？
- [ ] 本 Sprint 的新功能是否可以通过 Plugin 实现但被硬编码了？
- [ ] 本 Sprint 的 AI 调用是否有审计日志？
- [ ] 本 Sprint 的覆盖率是否下降？
- [ ] 本 Sprint 是否有硬编码的密钥或 Token？

## 9. 违规处理

### 9.1 违规分级

| 级别 | 定义 | 示例 | 处理 |
|------|------|------|------|
| **Critical** | 违反 P1-P4 硬约束 | 未经文档的架构变更 | 代码立即回滚 + RCA + 流程改进 |
| **Major** | 违反 P5-P8 强约束但无直接危害 | 新功能未以 Plugin 实现 | 限期整改（1 Sprint） |
| **Minor** | 程序性违规 | ADR 未获 2 人 Approve 就合并 | 补办程序 + 警告 |

### 9.2 紧急例外

- 安全漏洞热修复可绕过正常流程（事后 48h 内补文档和测试）
- 需要 Maintainer 明确批准
- 滥用紧急例外 → 取消该 Maintainer 的紧急批准权

## 11. 附录：原则的历史背景

### 为什么是这八条，不是六条也不是十条

八项原则的选定经历了多次迭代。最初的草案有 12 条，经过以下删减逻辑缩减到 8 条：

- **Performance First** 被删除——性能重要但不是架构原则。FastAPI + async + Redis Cache 已经足够。如果 Phase 3 出现性能瓶颈，在 ADR 中处理即可。
- **User First** 被删除——过于宽泛。UX 原则在产品策略文档中处理，不在宪法中。
- **Data First** 被合并到 Domain First 和 Architecture First 中——数据模型是领域模型的一部分，数据架构是系统架构的一部分。
- **Open Source First** 被合并到 Plugin First 中——开源是手段，插件化是架构。

### 原则的排序逻辑

P1-P4 是按"变化的代价"排序的：

- **Documentation First (P1)**: 文档是唯一不在代码仓库中的资产——丢失文档等于丢失设计意图。变化代价最高。
- **Architecture First (P2)**: 架构接口是模块间的合同——改接口影响所有消费者。变化代价高。
- **Domain First (P3)**: 领域模型是业务的镜像——业务不变，模型不变。但如果选错了领域划分，重构成本高。
- **API First (P4)**: API 是外部消费者的合同——改 API 影响所有第三方。变化代价最高（外部）。

P5-P8 是按"防护范围"排序的——从最广（Plugin 覆盖所有扩展场景）到最基础（Security 覆盖所有代码）。
