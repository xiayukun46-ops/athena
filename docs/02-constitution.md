# 02 — Project Constitution

> 本宪法是 Athena 项目的最高准则。所有设计、开发、决策均受其约束。

**参见详细版**: [governance/constitution.md](governance/constitution.md)

---

## 八项核心原则

按优先级从高到低排列。违反前四项的代码必须拒绝合并。

### P1. Documentation First（文档优先）

**规则**: 无设计文档，不写代码。

**为什么**: 代码会过时，设计意图不会。10 年项目必须有清晰的设计脉络。
**替代方案**: Code-as-documentation（代码即文档）。**不选理由**: 代码解释不了"为什么"，只能解释"是什么"。
**影响**: 每次 PR 必须附带文档更新。CI 自动检查关键文档是否存在。

### P2. Architecture First（架构优先）

**规则**: 先定义接口和契约，后写实现。

**为什么**: 接口是模块间的"法律"。先有法律，后有交易。
**替代方案**: 敏捷迭代（先写代码再抽象）。**不选理由**: 适合 3 个月的项目，不适合 10 年的项目。
**影响**: 新模块必须先通过接口设计评审（ADR）。

### P3. Domain First（领域优先）

**规则**: 代码组织围绕领域模型，不是技术分层。

**为什么**: 领域模型反映"业务是什么"。技术分层（controller/service/repository）反映"代码怎么写"。前者 10 年不变，后者可能 2 年一换。
**替代方案**: 传统 MVC 分层。**不选理由**: 跨层修改是常态，领域内聚更能抵抗变化。
**影响**: 目录结构按限界上下文组织：`src/content/`、`src/knowledge/`、`src/search/` 而非 `src/controllers/`。

### P4. API First（API 优先）

**规则**: 所有功能以 API 契约定义，前端和后端独立开发。

**为什么**: API 是 Athena 对外的"宪法"。先定宪法，各州自治。
**替代方案**: 后端驱动前端（Server-side rendering）。**不选理由**: 锁死客户端形态（Web only），不利于 Phase 5 的开放平台。
**影响**: 每个功能先在 OpenAPI 中定义，再实现。

### P5. Plugin First（插件优先）

**规则**: 核心最小化。所有业务能力通过插件实现。

**为什么**: 5 年后的需求现在无法预测。插件系统是应对不确定性的唯一方式。
**替代方案**: 核心集成所有功能。**不选理由**: 核心膨胀 → 维护困难 → 新人不敢改 → 项目僵化。
**影响**: 每种新的内容源类型、AI 模型、存储后端都以插件接入。

### P6. AI First（AI 优先）

**规则**: AI 不是功能，是架构原语。数据管道天然支持 Embedding、RAG、Agent 工作流。

**为什么**: 如果 AI 是"附加功能"，换模型需要重构数据管道。如果 AI 是"架构原语"，换模型就是换插件。
**替代方案**: 先建平台再加 AI。**不选理由**: 2026 年开始建非 AI 原生的知识平台，等于用马车设计高铁。
**影响**: 数据库天然支持向量（pgvector），API 设计支持异步 AI 任务（202 Accepted），领域事件触发 AI 管道。

### P7. Test First（测试优先）

**规则**: TDD。先写测试，后写实现。

**为什么**: 测试是"活的设计文档"。10 年项目中，测试是唯一保证"改了 A 没坏 B"的机制。
**替代方案**: 先写代码后补测试。**不选理由**: 补的测试测的是实现，不是设计。
**影响**: CI 中覆盖率门禁不可绕过。

### P8. Security First（安全优先）

**规则**: 零信任。默认不信任任何输入。

**为什么**: AI 系统有独特的安全挑战：Prompt 注入、模型数据泄露、知识投毒。
**替代方案**: 上线前做一次安全审查。**不选理由**: 事后补救永远比事前预防贵。
**影响**: 每次 PR 必须通过安全扫描（Trivy, Gitleaks）。

## 决策体系

```
L0: 本宪法 — 不可动摇
L1: ADR (Architecture Decision Record) — 重大架构决策，需 2 人 Approve
L2: RFC (Request for Comments) — 功能设计，社区讨论 ≥ 7 天
L3: PR Review — 日常代码决策
```

---

## 修订程序

- 修订提案以 RFC 形式提交
- 核心团队 ≥ 2/3 多数通过
- 旧版本归档，保留完整历史
